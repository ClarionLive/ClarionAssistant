# Clarion Assistant 5.8

5.8 is the release where **CodeGraph starts telling the truth, thirty times faster**. A full index of a 27-app production solution fell from over an hour to under three minutes, and the same field testing that measured it found the index had been answering "who calls this?" with the wrong procedure entirely, skipping every routine body, and never indexing a procedure whose label contains a colon &mdash; which in generated Clarion is the whole referential-integrity layer. All of it is fixed, measured, and visible: indexing now opens a progress window you can cancel, and writes a transcript that survives the IDE.

The other headline is an apology. **Installing Clarion Assistant overwrote your Claude Code settings** &mdash; every install, on every machine, since the configuration step was written. That is fixed, the damage is recoverable, and the entry below tells you where to find your file.

Also here: Mark Sarson's **Markdown editor** ships in the installer, the **CA Embeditor** attaches in colon-named procedure suites ([#196](https://github.com/ClarionLive/ClarionAssistant/issues/196)), two Clarion environments no longer share one application history ([#197](https://github.com/ClarionLive/ClarionAssistant/issues/197)), asking the assistant to build compiles what is actually on your screen, and documentation search stops mangling accented characters.

**Supported:** Clarion 10, 11, 11.1, and 12 (32-bit IDE). The installer lets you pick which version(s) to install.

> **Re-index your solutions and re-import your documentation after updating.** Both sets of fixes correct what gets *read*, not what is already stored, so existing databases keep their old blind spots until re-run.

## Highlights

### 🛡️ Installing no longer wipes your Claude Code settings ([#190](https://github.com/ClarionLive/ClarionAssistant/issues/190))

**Every install, on every machine, overwrote `%USERPROFILE%\.claude\settings.json`** &mdash; Claude Code's own global configuration, a file Clarion Assistant does not own. What came back contained only the handful of keys the installer itself writes. Everything else was gone: `hooks`, `statusLine`, `model`, `tui`, your enabled plugins and marketplaces, and your own entries under `permissions.allow`. Losing `hooks` is the worst of it, because nothing announces it &mdash; your automation simply stops running.

The installer runs its configuration step under Windows PowerShell 5.1, and the script asked for a JSON-parsing option that only exists in PowerShell 6 and later. So the parse failed every time. What destroyed anything was the error handler: it mistook its own unsupported call for a corrupt settings file, said so, backed the file up, and rebuilt it from empty.

**If this happened to you, your settings are still on disk.** Look next to the file for `settings.json.backup.` followed by a timestamp &mdash; that name is ours, written by the code path described above, so its presence is the signature of this bug. The most recent one is your file as it was immediately before the install.

Three things changed, because the parse was the trigger rather than the whole defect. The parse now works on both PowerShell versions, preserving your key order and the shape of single-element lists so the file it writes back can still be diffed against a copy you kept. A parse failure that is *genuine* now backs the file up, reports what the parser actually said, and **leaves your file alone**. And because this script only ever adds keys, it now refuses to write at all if a top-level key that was present when it loaded has gone missing &mdash; a check that is not specific to this bug and would have caught it.

Underneath, the installer build now parse-checks every one of its scripts in a real PowerShell 5.1 host and **fails the build** if any of them would not load there. This shipped because nothing ever ran that script under the version it actually runs on.

### ⚡ Indexing is thirty times faster

The hour-long index is gone. Measured on the same 27-app production solution: a full index that took **1:12** now completes in **2:42** inside the IDE, and 1:53 from the standalone indexer. The cost was never the disk &mdash; the relationship pass was testing every line of code against all six thousand callable names, one substring scan at a time. It now splits each line into identifiers once and looks them up in a hash table, and a full row-by-row comparison of the old and new databases (347,203 symbols, 1,023,354 relationships) confirmed the output is **identical to the edge**.

An **Update** with nothing changed returns in a quarter of a second; with changes it costs about the relationship pass (~2 minutes on a solution this size), since relationship resolution still rebuilds solution-wide. Two indexes can no longer collide: starting one while another is writing the same database &mdash; from the toolbar or from either MCP tool &mdash; is refused with a clear message instead of silently corrupting the graph.

### 🔍 CodeGraph stops giving confidently wrong answers about who calls what

Field testing found that "who calls X" could answer with the wrong X entirely. Where the same procedure name exists in several apps &mdash; and in generated Clarion code, dozens do &mdash; every call in every app resolved to one arbitrary copy. Not missing answers. Wrong ones.

Call resolution is now scoped the way the compiler thinks: the same file first, then the same project, then the projects yours actually depends on. Every one of those 27 apps now resolves calls to its own copy, and the share of calls crossing project boundaries fell from 49% to the 24% that genuinely are DLL calls. Where several same-named overloads truly cannot be told apart, the pick is deterministic and **marked** &mdash; a new `ambiguous` flag says "one of several" instead of asserting certainty the index does not have.

Four more answers the graph could not previously give:

**"Is this the declaration or the body?"** MAP prototypes and real implementations carried identical rows, making go-to-definition a coin flip &mdash; and quietly poisoning the documented dead-code query, which turned out to return **98.7% false positives** because it filtered on exactly the prototype rows, which never receive calls. A new `decl_kind` column separates prototype, implementation and external; the dead-code recipe is corrected in the docs, and calls never resolve to a prototype when a body exists.

**"Where does DO go?"** Routine calls &mdash; the primary control flow inside any generated Clarion procedure &mdash; were never captured at all. The schema documented the edge type and there were zero rows, partly because routine labels containing colons (`BRW10::ProcessScroll`, which is to say most of them) did not even match the pattern. That solution now carries 29,326 of them.

**"Which of these eight is the real one?"** A global declared in one DLL appears in every app that imports it, and the rows were indistinguishable. Externals are now marked as such, and every symbol carries its declaration line in `source_preview`, so results explain themselves without opening a file. References to an external also **re-point to the owning declaration** &mdash; previously each app handed its usage edges to its own local import row, so the declaration you actually navigate to looked nearly unused.

**"What breaks if I delete from this table?"** A procedure whose label contains a colon was never indexed as a procedure at all. In template-generated code that is the entire referential-integrity layer &mdash; every `RIDelete:` and `RIUpdate:`, nearly nineteen thousand declarations in the test solution &mdash; and because the relationship scanner shared the blind spot, whole `_RD`/`_RU` files contributed no edges: the cascade-delete graph simply did not exist. One character class in four patterns; the fix gained 31,860 symbols and 52,483 relationships.

Two deeper cuts landed with them. **Routine bodies were never scanned** &mdash; a `ROUTINE` label switched the scanner off, and in generated Clarion most of the real work lives in routines &mdash; and the everyday statement `DO ProcedureReturn` **prefix-matched the PROCEDURE pattern**, so the scanner believed a procedure named "DO" had just been declared and stopped reading the body there. One missing word boundary, quietly amputating scans since the beginning. Together they took the solution from 478 thousand relationships to **1.1 million**: false "dead routine" readings fell from 60% to 9%, unused-variable false positives on locals from 64% to 37%, and class data members &mdash; previously 100% blind &mdash; now receive reference edges.

### 📈 Indexing finally shows its work

Starting an index now opens a **progress window**: every app listed up front and ticked off as it parses, the file being read right now, a progress bar weighted by where the time actually goes, elapsed time, and an estimate seeded from your previous run until live throughput takes over.

Indexing can be **cancelled** mid-run. A cancelled full index deletes the partial database rather than leaving something that would quietly pass for a complete one; a cancelled update keeps your old data and says plainly not to trust it until re-run. When the run finishes the window becomes the report &mdash; symbols, relationships, duration, warnings &mdash; with one button to copy the summary and another to open the **full transcript**, which is now always written to `%APPDATA%\ClarionAssistant\codegraph-index.log` (one file per solution, previous run kept) so it survives even if the IDE does not. The window also no longer steals focus from the IDE while you work.

### 🧭 The index sees more than twice as much of your solution &mdash; including, at last, your globals

The index went from 170 thousand symbols to 385 thousand, and from 53 thousand call relationships to 392 thousand. Not from new cleverness in the parser &mdash; from finally looking where your code actually is.

The biggest miss was the redirection file. The indexer resolved source by convention and only consulted a `.red` if one sat next to the `.sln`. Most installs keep it in the Clarion `bin` folder, so every file your `.red` places elsewhere silently fell off the index. It now uses the same active redirection the IDE has loaded, and the standalone indexer takes `--red`.

Second: **global data was never indexed.** The declaration section of your main PROGRAM file &mdash; six thousand lines of it in one app we measured &mdash; was skipped entirely, so no global variable, GROUP or EQUATE existed anywhere in the graph. Declarations sized with nested parentheses, `CSTRING(CHR(10))`, also no longer vanish. A routine's own `DATA` block was likewise never scanned: 9,261 routine-local variables across 890 generated files did not exist in the index.

The two indexing tools also stopped disagreeing &mdash; `index_codegraph` ran without the library paths and redirection `index_solution` used, so how complete your database was depended on which had run last. They share one implementation now, include chains are followed recursively instead of one level deep, and the addin and standalone indexer build from one shared source instead of two copies that had already drifted.

Finally, the index audits itself. Every file the indexer touches gets a row in a new `indexed_files` table saying what happened to it &mdash; parsed, empty, unresolved, or skipped and why &mdash; and the run ends by naming anything that did not resolve rather than leaving silence. On its first real run that audit caught a genuine bug: two files whose `$`-containing names the project file stores percent-encoded, which the indexer had been dropping without a trace.

### 📡 The index tools stream their progress

`index_solution` and `index_codegraph` were the same spinning cursor in MCP form: an hour of silence and then a wall of text &mdash; or worse, "index started" and no way to know it finished. With a progress-capable client (the in-IDE Claude tab qualifies), both now stream **live progress**, and `index_solution` waits for the run and returns real completion stats: symbols, relationships, duration, database path, and where the transcript landed. Long calls stay alive through the progress stream itself; a three-minute index was verified end to end without a client timeout. Clients that do not send a progress token get exactly the old behaviour.

### 📝 The Markdown editor now installs with Clarion Assistant &mdash; the maintained one

Markdown files have been openable in the IDE for a while, but only if you went and found the addin yourself. It now ships in the installer, pinned to a specific upstream release the same way the bundled language server is.

The version that ships is [Mark Sarson's](https://github.com/msarson/ClarionMarkdownEditor), which began as our own editor and has been developed well past it since. Pointing our installer at the maintained line means one editor to report problems against instead of two drifting copies, and it is why a markdown question is best raised upstream rather than here. It installs as its own addin, not as part of Clarion Assistant, because that is what it is &mdash; useful whether or not you use any AI tooling, and removable on its own.

**If you already have it, we will not touch it unless ours is newer.** The check reads the version out of the addin's own manifest rather than trusting the DLL's version resource, which upstream leaves frozen at `1.0.2.0` across every release &mdash; so anyone tracking upstream directly, or installing through Mark's addin finder, keeps the newer copy. The MIT licence travels with it, and the installer build now fails outright if that notice ever goes missing.

### 🧩 The CA Embeditor attaches in colon-named procedure suites ([#196](https://github.com/ClarionLive/ClarionAssistant/issues/196))

On a generated application where every procedure is named like `reg:TENDER:GiftCard`, the CA Embeditor's auto-overlay had never attached &mdash; not once. The reporter's own logs across six weeks tell it precisely: 72 attach triggers, 65 name-resolution skips, 6 successes, and all 6 successes were procedures whose labels happened to carry no colon.

The procedure-name matcher simply did not allow a colon in a label. Against a real declaration it took `r`, then `eg`, then required whitespace and met `:` instead. The name came back empty, and rather than guess the overlay treated that as a failure and aborted. The generated module name is no fallback either, because Clarion flattens the colons on the way to disk (`reg_TENDER_GiftCard.clw`), so it does not lead back to a real procedure name.

Colons are ordinary in Clarion labels, and this is the second place in this release where assuming otherwise hid a whole class of code from a feature. Every hardening property the matcher already had is preserved and was checked against fixtures rather than argued: indented `MAP` prototypes are still excluded, and so are dotted ABC method labels like `ThisWindow.Init`.

### 🗂️ Two Clarion environments no longer share one application history ([#197](https://github.com/ClarionLive/ClarionAssistant/issues/197))

If you run more than one Clarion environment from a single installation &mdash; using Clarion's own `/ConfigDir=` switch, which points it at a separate settings folder &mdash; Clarion Assistant merged their application histories into one. Clarion itself kept the two environments properly apart; only CA ran them together.

CA never asked the IDE where its settings live. It rebuilt the path from the running executable's version stamp instead, which works right up until two environments produce the same stamp &mdash; and Clarion 11 and 11.1 both report themselves as `11.0`. Both therefore resolved to the same settings file, the same install root and the same identity.

CA now asks, in order of authority: the IDE's own configuration directory, then the `/ConfigDir=` switch read from the command line for the case where the question is asked before the IDE has finished starting, and otherwise nothing at all &mdash; it never guesses a path. **This is migration-free.** A default installation resolves to exactly the string it did before, so no existing history moves; only a settings folder outside the default location gets a distinct key, and that key is stable across the same path written in different cases or with quotes. A `[config-dir]` line in the diagnostic log names what was resolved, so the outcome is readable rather than inferred.

### 🤖 The embedded assistant knows about every tool it has &mdash; this time in the copy that ships

An audit before 5.7 found 51 registered tools documented nowhere in the assistant's system prompt &mdash; the build tools, TXA/DCTX import and export, SchemaGraph, Everything search, multi-instance coordination, generation traces and more. The assistant never reached for them, because as far as its instructions were concerned they did not exist.

That audit landed in the wrong file. The prompt lives in two places: a bundled copy the installer ships, and a per-project copy the addin writes on every terminal start. The fix went into the second, which is overwritten from the first each time &mdash; so the repository was correct and every shipped build was not. **5.7 went out with the July 30 prompt, still missing all 51.**

Both copies are now the same document, and a check enforces that they stay that way: it fails loudly on drift and names the tools the shipped prompt would omit, since the whole failure mode here was staying quiet. Auditing that fix turned up a *third* copy &mdash; the installer also wrote `clarion-assistant-reference.md` into your `.claude` folder from a separate hand-maintained file, drifted further still, with eight whole tool sections missing and a tool documented that no longer exists. It is gone; the reference now comes from the same bundled prompt as everything else.

If you noticed the assistant ignoring a tool you knew it had, this was why.

## 🐞 Fixed

### Editor

- **Asking the assistant to build now compiles what is on your screen.** Editing a `.clw` in the CA Editor and asking the assistant to build compiled the *last saved* version. The toolbar build button had saved unsaved editors since July; the assistant's build tools went straight out to `ClarionCL` without entering the IDE's build pipeline, so the hook that does the saving was never reached. `build_solution`, `build_app` and `generate_source` now flush the editor first. Building a C# project and the bare command passthrough deliberately do not &mdash; writing your files as a side effect of an arbitrary command would be a surprise.
- **Saving no longer throws the caret to the top of the file.** Nothing was reloading, which is what made this hard to read: the native editor still has the same file open underneath, so our own write looks to it like an external change, and it reloads and parks its caret at line 1. The mechanism that mirrors the native caret into the visible editor &mdash; the one that makes Errors-pane, Bookmarks and Find Next land correctly &mdash; then faithfully carried that reset across. Suppression is deliberately narrow: line 1 only, and only within two seconds of our own write, because that pairing is the exact signature. This applied to plain **Ctrl+S** too; the build only made it obvious.
- **The editor no longer thinks a saved file is unsaved.** A build-triggered save cleared the host's record but never told the page, which kept its unsaved-changes dot and kept treating the work as existing only in its buffer &mdash; something both its close path and its external-change handling branch on. The confirmation now echoes the edit it is confirming, so typing between the save and the acknowledgement correctly leaves the editor dirty rather than marking live keystrokes as saved.
- **Template files listed in the editor settings now actually open in the editor.** `.tpl` and `.tpw` were in the Editor Surfaces file-type list out of the box and adding them changed nothing. The setting was not being ignored &mdash; it was never consulted, because the IDE only ever offered our editor the file types the stock Clarion editor already handles. Our editor now also claims the types you have explicitly listed, and only those: it adds to what the stock editor would have opened and never takes anything away. Underneath, writing an entry the way file filters are normally written &mdash; `*.tpl` rather than `.tpl` &mdash; produced a pattern that could never match any file, silently. Both spellings work now, as does `tpl`, and `*.*` no longer turns "every file" into "no files".
- **The save-before-build hook can finally be observed.** "Never fired", "failed to subscribe", "fired and found nothing to save" and "working perfectly" were byte-identical in the log &mdash; four states, one silence, which is why a user report could be neither confirmed nor refuted. The next single build now says which.

### Documentation search

- **Accented characters are no longer mangled.** Every non-ASCII character in the ingested documentation came back corrupted &mdash; em-dashes as `&acirc;&euro;&rdquo;`, "Inicio Rápido" as "Inicio RÃ¡pido". The documents were never at fault; they declare `<meta charset="UTF-8">` and are valid UTF-8 on disk. The ingester read them as the machine's ANSI codepage instead &mdash; and not by forgetting an argument, which is why it survived two previous encoding sweeps: the wrong encoding was passed *explicitly*, so an audit hunting for reads that omitted one walked straight past it. HTML is the one format here that declares its own character set, so it now gets a ladder that respects that: byte-order mark, then the document's own declaration, then a validating UTF-8 attempt, then ANSI. A document claiming UTF-8 is deliberately not taken at its word &mdash; it is verified, so a mislabelled file falls back rather than filling your results with replacement characters. Measured against the affected documents the corruption goes to zero: 240 occurrences in one Spanish reference, 7 in its English counterpart, none introduced anywhere. **Re-import any documentation you have already ingested.**

### Assistant

- **The assistant picks up what it was left waiting on.** Deploying a new build closes the assistant's terminal, and anything it had been asked to do next died with it &mdash; which is the worst possible moment to lose the thread, because waiting for that deploy is usually *why* something was still outstanding. It now records outstanding work the moment it becomes blocked rather than at the end of a session, since a session that ends by being killed has no end to write at, and leads with what was pending on its next start.
- **Clarion Assistant terminals leave the MultiTerminal roster when they close.** If you use MultiTerminal alongside the IDE, its roster filled with CA terminals that no longer existed. Three separate defects were each enough on their own: the exit event was raised from one place guarded by a flag that closing the tab had already cleared, so it only ever fired when a terminal died on its own; a closed tab was removed from the list *before* being disposed, so no later sweep could see it; and `localhost` stalled every call until it timed out, because MultiTerminal listens on IPv4 only, Windows resolves `localhost` to the IPv6 address first, and .NET does not fall back within the timeout the way `curl` and `node` do &mdash; measured at 1572ms to fail against 13ms to succeed on `127.0.0.1`. That last one was not confined to the disconnect: the Agents pad polls the same client every eight seconds, so every one of those polls had been dying at its ten-second timeout and that pad was never showing live data.

### Build and release

- **A release could ship with no language server and say so almost silently.** Building in a fresh checkout produced an addin with no language server in it. The only sign was a single grey line among thirty green ones, and it happened only on the *first* build in a new tree, which made it look like flaky timing rather than a defect. The deploy script had captured the language-server build's own console output as if it were the path that build returned; the path was still in there, last, behind everything git and npm had printed. What made it dangerous is how it failed &mdash; the check guarding the copy still passed, so the step looked alive while quietly skipping the server. The installer build now also **fails outright** when the compiler reports a component shipping absent, rather than noting it in passing.
- **Deploying updates every live installation of a Clarion version**, not just the first one found.

## ⚠️ Known issues

- **Native Access Violation in Clarion's Generator on closing an embeditor** ([#179](https://github.com/ClarionLive/ClarionAssistant/issues/179)) &mdash; "Internal error: Restore Procedure". Still open, and likely the same underlying step behind the stale window-designer error icons in [#142](https://github.com/ClarionLive/ClarionAssistant/issues/142).
- **A document can still be closed and re-opened from scratch after a build**, which moves the caret. This is distinct from the caret fix above &mdash; that one is closed, and the log now rules it out cleanly &mdash; but what triggers the re-open is not yet identified.
- **Existing CodeGraph databases and DocGraph libraries keep their old answers until re-run.** Every improvement in this release corrects what gets read, not what is already stored. Re-index your solutions and re-import your documentation.

## 📦 Install

1. Download **`ClarionAssistant-5.8-Setup.exe`** below (code-signed).
2. Close the Clarion IDE.
3. Run the installer and pick your Clarion version(s) (10 / 11 / 11.1 / 12). Each row installs the build for **that** version &mdash; if you have two installations of the same version, add both folders to that row with the **`+`** button.
4. Start Clarion &mdash; the **Clarion Assistant** pane docks automatically (Tools → Clarion Assistant, or Ctrl+Alt+C).
5. **Re-index your solutions** (CodeGraph) and **re-import your documentation** (DocGraph) to pick up this release's indexing and encoding fixes.

Upgrading from 5.1&ndash;5.7 installs cleanly over the top.
