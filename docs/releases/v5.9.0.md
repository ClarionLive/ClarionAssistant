# Clarion Assistant 5.9.0

> **DRAFT.** Written by Charlie for John to edit. Coverage is complete against the 22 commits since
> v5.8.1 and every factual claim below is checked against the source or the commit that made it.
> The voice is not final.

**5.9.0 is about the CA Embeditor behaving like the rest of Clarion, and about our version number
finally meaning one thing.** The embeditor half is mostly keys and dialogs: shortcuts that used to
vanish now reach the IDE, and closing unsaved work asks before discarding it — using Clarion's own
prompt rather than an imitation of it. The version half is groundwork: Clarion Assistant is joining
the **Clarion Addin Registry**, so it can be discovered and updated from **AddinFinder** inside the
IDE, and that requires a version number the manifest, the installer and the git tag all agree on.

**Supported:** Clarion 10, 11, 11.1, and 12 (32-bit IDE).

> **Why the jump from 5.8.1 to 5.9.0?** Not marketing. AddinFinder only ever lets a recorded version
> move *forward*, comparing component by component — and our manifests have been reporting build
> numbers like `5.8.1165` for years. Against that, `5.8.2` compares as **lower** (2 against 1165),
> which would have left every existing user permanently told an update was available while looking
> perfectly correct on any fresh install. Details below.

---

## CA Embeditor: the keys that used to do nothing ([#192](https://github.com/ClarionLive/ClarionAssistant/issues/192))

Inside a CA Embeditor, most of Clarion's own shortcuts went nowhere. The editor has focus, the
editor consumes the key, and the IDE never hears it.

**Ctrl+F4**, **Ctrl+O** and **Alt+&lt;letter&gt;** now reach the IDE. The interesting one is
`Alt+<letter>`: rather than a hardcoded table of letters, the key is matched against the **real menu
mnemonics** the IDE is currently showing, so it keeps working if the menus change and it never
claims a letter that has no menu behind it.

All three route through the workbench menu itself. That is the point: the IDE then does exactly
what it would normally do, rather than us reimplementing a close or an open and slowly drifting away
from the real behaviour.

## CA Embeditor: Ctrl+F4 on unsaved work now asks

Closing a dirty CA Embeditor with Ctrl+F4 **discarded the edits without asking**. The CA Editor
prompted on close and the embeditor did not, which made the difference look arbitrary — and it was
the sort of thing you only discover by losing work.

**The prompt was never broken.** Clarion raises its own *"Save Changes in Embed Editor?"* dialog
from `CommonGenEditor.TryClose()`, which decides by consulting the **native** editor's dirty flag.
Our Monaco overlay sits on top of that native editor and never set the flag, so Clarion looked,
saw a clean embed, and closed it.

The fix is ordering rather than machinery. On Ctrl+F4 the page sees the key before the host
dispatches it, so it flushes the Monaco edits into the native embed and sets the dirty flag
**first**, then posts the key. Host messages process in order on the UI thread, so by the time
`File > Close > File` runs, Clarion has a genuinely dirty embed and raises **its own** dialog. Exact
parity by construction — there is no second dialog to keep in step.

That ordering also fixes a quieter bug that would have been worse than the missing prompt: answering
**Yes** now saves the edits you can see, not the stale native buffer underneath them.

The toolbar's **red X** asks as well, worded to match Clarion's dialog. That one could not be
delegated — our toolbar replaced the native close button, so cancelling never reaches Clarion's
close path at all. Answering **Cancel** to either leaves you editing, with your work still
protected.

## CA Embeditor: an orphaned overlay is now torn down for real

When the native embed closes underneath the overlay — Errors-pane navigation opening the module
source, a native cancel, an app-gen regeneration — the overlay keeps its text and still looks
perfectly healthy. What follows is confusing rather than dramatic: **Save** reports *"nothing to
save"*, and **Cancel** blanks the buffer.

A teardown hook existed for exactly this condition, and it had **never once fired**. It subscribed
to a `Disposed` event that does not exist on that class in this Clarion fork, and the null check
guarding the subscription swallowed the failure silently — so the safety net read as present in the
source while being connected to nothing at all. Downstream code had grown defensive guards to
compensate for a backstop that was never there.

## Ctrl+Q shows Clarion's confirmation, not ours ([#193](https://github.com/ClarionLive/ClarionAssistant/issues/193))

The Ctrl+Q confirmation was a web-styled dialog sitting in the middle of a native IDE, and it
looked it. It is now the **native Windows dialog**, and it is scoped to the embeditor rather than
firing globally.

## Installing no longer corrupts non-ASCII characters in settings.json ([#200](https://github.com/ClarionLive/ClarionAssistant/issues/200))

A follow-on to [#190](https://github.com/ClarionLive/ClarionAssistant/issues/190), with the same
root cause wearing different clothes: the installer's configuration step runs under **Windows
PowerShell 5.1**, where two defaults are not what the code appears to say.

**Three defects, all in `installer/configure.ps1`:**

1. **The read was ANSI.** `Get-Content` with no `-Encoding` decodes using the system codepage on
   5.1. A BOM-less UTF-8 `settings.json` therefore had every non-ASCII character mangled on the way
   *in*, and the mangled form written back out. Measured on a real 5.1 host: a typographic
   apostrophe (`’`, bytes `e2 80 99`) came back as `â€™`.
2. **The write added a BOM.** `Set-Content -Encoding UTF8` means UTF-8 **with** BOM on 5.1 and
   **without** on PowerShell 7 — the two hosts disagree about what that token names, which is
   exactly why the call read as correct.
3. **A successful merge kept no backup.** A copy was written only when the installer *refused* to
   write — a parse failure, or the dropped-key guard. The common case, a merge that worked,
   overwrote in place with nothing kept. The 5.8 notes told affected users to look for a
   `settings.json.backup.<timestamp>` that path never produced.

All three are fixed. A backup is now written before the file is overwritten, and a file already
BOM'd by a 5.8 install is read correctly *and* cleaned. The same two encoding fixes were applied to
the `.clarioncom.env` file in the same script, where a Windows account name containing a non-ASCII
character would otherwise have been mangled on every re-run.

**What cannot be fixed:** characters already mangled on disk. The original bytes are gone from the
damaged file, and because of the third defect there is no backup to restore from.

The configuration script is now covered by a **regression test** that runs the real script under a
real 5.1 host and checks the result byte by byte. It runs the unfixed code first as a control: if
that fails to reproduce the corruption on the machine it is running on, it reports "could not run"
rather than passing, so a green result cannot be a false one.

## Version numbers now mean one thing

The released version is **Major.Minor.Patch** — one value, shared by `Version.props`, the addin
manifest and the git tag.

Before this, the third component was a build counter that incremented on **every compile**. The
manifest said `5.8.1165`, the release was tagged `v5.8.1`, and the installer script carried a third,
hand-maintained `5.8.1`. Three sources of truth, two of them updated by remembering to.

That matters now because **AddinFinder compares the version in the installed manifest against the
latest release tag**, and reports *"Update available"* on any difference — a message that
reinstalling cannot clear, because the manifest simply reasserts the same number.

**And it is why this release is 5.9.0.** AddinFinder only ever lets a recorded version move
*forward*. Against an existing entry of `5.8.1165`, the number `5.8.2` compares as lower — 2 against
1165 — so the update would have been refused and the message would have stuck. Fresh installs take
the manifest value directly, with no such rule, so `5.8.2` would have looked entirely correct on any
machine that had never had Clarion Assistant before, and been broken on every machine that had.

The build counter has not gone away. It still increments on every compile and still appears in the
DLL's file properties and in the docked pad's title (`5.9.0.1165`), where it is genuinely useful for
support. It simply no longer appears in the one string that has to match a git tag.

Two guards now enforce this: the build **fails** if the manifest and `Version.props` disagree, and
the installer script no longer holds a copy of the version at all — it is passed in at build time
and the script refuses to compile without it.
