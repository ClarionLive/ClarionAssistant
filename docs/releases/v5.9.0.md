# Clarion Assistant 5.9.0

> **DRAFT.** Written by Charlie for John to edit. Coverage is complete against every commit since
> v5.8.1 and every factual claim below is checked against the source or the commit that made it.
> The voice is not final.

**5.9.0 is about the CA Embeditor behaving like the rest of Clarion, and about our version number
finally meaning one thing.** The embeditor half is mostly keys and dialogs: shortcuts that used to
vanish now reach the IDE, and closing unsaved work asks before discarding it — using Clarion's own
prompt rather than an imitation of it. The version half is groundwork: Clarion Assistant is joining
the **Clarion Addin Registry**, so it can be discovered and updated from **AddinFinder** inside the
IDE, and that requires a version number the manifest, the installer and the git tag all agree on.
And on very large procedures, completion, hover and squiggles in the CA Embeditor are now instant.
Before, they waited seconds or minutes on the language server. The pane's header also gains
**Solution / Schema Sources / Source Control** tabs, so the solution's settings are no longer hidden
inside each chat tab.

**Supported:** Clarion 10, 11, 11.1, and 12 (32-bit IDE).

> **Why the jump from 5.8.1 to 5.9.0?** Not marketing. AddinFinder only ever lets a recorded version
> move *forward*, comparing component by component — and our manifests have been reporting build
> numbers like `5.8.1165` for years. Against that, `5.8.2` compares as **lower** (2 against 1165),
> which would have left every existing user permanently told an update was available while looking
> perfectly correct on any fresh install. Details below.

## CA Embeditor: the keys that used to do nothing ([#192](https://github.com/ClarionLive/ClarionAssistant/issues/192))

Inside a CA Embeditor, most of Clarion's own shortcuts went nowhere. The editor has focus, the
editor consumes the key, and the IDE never hears it.

**Ctrl+F4**, **Ctrl+O** and **Alt+&lt;letter&gt;** now reach the IDE. The interesting one is
`Alt+<letter>`: rather than a hardcoded table of letters, the key is matched against the **real menu
mnemonics** the IDE is currently showing, so it keeps working if the menus change and it never
claims a letter that has no menu behind it.

All three route through the workbench menu itself. That is the point: the IDE then does exactly
what it would normally do, rather than us reimplementing a close or an open and slowly drifting away
from the real behaviour.

## CA Embeditor: Ctrl+F4 on unsaved work now asks

Closing a dirty CA Embeditor with Ctrl+F4 **discarded the edits without asking**. The CA Editor
prompted on close and the embeditor did not, which made the difference look arbitrary — and it was
the sort of thing you only discover by losing work.

**The prompt was never broken.** Clarion raises its own *"Save Changes in Embed Editor?"* dialog
from `CommonGenEditor.TryClose()`, which decides by consulting the **native** editor's dirty flag.
Our Monaco overlay sits on top of that native editor and never set the flag, so Clarion looked,
saw a clean embed, and closed it.

The fix is ordering rather than machinery. On Ctrl+F4 the page sees the key before the host
dispatches it, so it flushes the Monaco edits into the native embed and sets the dirty flag
**first**, then posts the key. Host messages process in order on the UI thread, so by the time
`File > Close > File` runs, Clarion has a genuinely dirty embed and raises **its own** dialog. Exact
parity by construction — there is no second dialog to keep in step.

That ordering also fixes a quieter bug that would have been worse than the missing prompt: answering
**Yes** now saves the edits you can see, not the stale native buffer underneath them.

The toolbar's **red X** asks as well, worded to match Clarion's dialog. That one could not be
delegated — our toolbar replaced the native close button, so cancelling never reaches Clarion's
close path at all. Answering **Cancel** to either leaves you editing, with your work still
protected.

## CA Embeditor: an orphaned overlay is now torn down for real

When the native embed closes underneath the overlay — Errors-pane navigation opening the module
source, a native cancel, an app-gen regeneration — the overlay keeps its text and still looks
perfectly healthy. What follows is confusing rather than dramatic: **Save** reports *"nothing to
save"*, and **Cancel** blanks the buffer.

A teardown hook existed for exactly this condition, and it had **never once fired**. It subscribed
to a `Disposed` event that does not exist on that class in this Clarion fork, and the null check
guarding the subscription swallowed the failure silently — so the safety net read as present in the
source while being connected to nothing at all. Downstream code had grown defensive guards to
compensate for a backstop that was never there.

## Ctrl+Q shows Clarion's confirmation, not ours ([#193](https://github.com/ClarionLive/ClarionAssistant/issues/193))

The Ctrl+Q confirmation was a web-styled dialog sitting in the middle of a native IDE, and it
looked it. It is now the **native Windows dialog**, and it is scoped to the embeditor rather than
firing globally.

## Installing no longer corrupts non-ASCII characters in settings.json ([#200](https://github.com/ClarionLive/ClarionAssistant/issues/200))

A follow-on to [#190](https://github.com/ClarionLive/ClarionAssistant/issues/190), with the same
root cause wearing different clothes: the installer's configuration step runs under **Windows
PowerShell 5.1**, where two defaults are not what the code appears to say.

**Three defects, all in `installer/configure.ps1`:**

1. **The read was ANSI.** `Get-Content` with no `-Encoding` decodes using the system codepage on
   5.1. A BOM-less UTF-8 `settings.json` therefore had every non-ASCII character mangled on the way
   *in*, and the mangled form written back out. Measured on a real 5.1 host: a typographic
   apostrophe (`’`, bytes `e2 80 99`) came back as `â€™`.
2. **The write added a BOM.** `Set-Content -Encoding UTF8` means UTF-8 **with** BOM on 5.1 and
   **without** on PowerShell 7 — the two hosts disagree about what that token names, which is
   exactly why the call read as correct.
3. **A successful merge kept no backup.** A copy was written only when the installer *refused* to
   write — a parse failure, or the dropped-key guard. The common case, a merge that worked,
   overwrote in place with nothing kept. The 5.8 notes told affected users to look for a
   `settings.json.backup.<timestamp>` that path never produced.

All three are fixed. A backup is now written before the file is overwritten, and a file already
BOM'd by a 5.8 install is read correctly *and* cleaned. The same two encoding fixes were applied to
the `.clarioncom.env` file in the same script, where a Windows account name containing a non-ASCII
character would otherwise have been mangled on every re-run.

**What cannot be fixed:** characters already mangled on disk. The original bytes are gone from the
damaged file, and because of the third defect there is no backup to restore from.

The configuration script is now covered by a **regression test** that runs the real script under a
real 5.1 host and checks the result byte by byte. It runs the unfixed code first as a control: if
that fails to reproduce the corruption on the machine it is running on, it reports "could not run"
rather than passing, so a green result cannot be a false one.

## Version numbers now mean one thing

The released version is **Major.Minor.Patch** — one value, shared by `Version.props`, the addin
manifest and the git tag.

Before this, the third component was a build counter that incremented on **every compile**. The
manifest said `5.8.1165`, the release was tagged `v5.8.1`, and the installer script carried a third,
hand-maintained `5.8.1`. Three sources of truth, two of them updated by remembering to.

That matters now because **AddinFinder compares the version in the installed manifest against the
latest release tag**, and reports *"Update available"* on any difference — a message that
reinstalling cannot clear, because the manifest simply reasserts the same number.

**And it is why this release is 5.9.0.** AddinFinder only ever lets a recorded version move
*forward*. Against an existing entry of `5.8.1165`, the number `5.8.2` compares as lower — 2 against
1165 — so the update would have been refused and the message would have stuck. Fresh installs take
the manifest value directly, with no such rule, so `5.8.2` would have looked entirely correct on any
machine that had never had Clarion Assistant before, and been broken on every machine that had.

The build counter has not gone away. It still increments on every compile and still appears in the
DLL's file properties and in the docked pad's title (`5.9.0.1165`), where it is genuinely useful for
support. It simply no longer appears in the one string that has to match a git tag.

Two guards now enforce this: the build **fails** if the manifest and `Version.props` disagree, and
the installer script no longer holds a copy of the version at all — it is passed in at build time
and the script refuses to compile without it.

## The About box shows the full version

The About box reported `5.9` where everything else reports `5.9.0.1165`. It was building the string
from the assembly version's Major and Minor components only, so the patch and the build counter —
the two parts that actually distinguish one install from another — were dropped on the floor.

It now shows all four. That matters mainly for support: the build counter is how you tell a deployed
build apart from the one before it, and reading it off the About box is the fastest way to get it.

## The VS Code import preview no longer promises a font it cannot deliver

Importing settings from VS Code shows a preview of what will change. Where **Follow Clarion's editor
options** is ticked, some of those values are owned by the IDE rather than by the pad, and the
preview already warned about that on the indentation rows.

It did not warn on **Font size** and **Font family**, which are follow-mode-owned too. So the preview
offered a font change, the import stored it correctly, and the editor carried on showing the IDE's
font — which leaves the setting looking silently ignored. Unticking follow-mode reveals the imported
value was there the whole time.

The warning now appears on the font rows as well, and only when the IDE is actually reporting a font,
so it never warns about a setting that would in fact have applied.

## Bundled skills: the marketplace ones said .NET 4.8, the templates build 4.7.2

The ClarionCOM skills that ship with Clarion Assistant told you your project targets **net48**. Both
shipped templates target **net472** — `ClarionCOMTemplate.csproj` and `WebView2Template.csproj`
alike.

That is not a label being out by a decimal point. The deployment skill sent you to copy build output
from `bin/Release/net48/`, **a path MSBuild never writes**, and the control checklist would fail a
correctly configured project. Corrected throughout the four affected skills.

The blanket rule against generating Clarion code was also too broad, and is narrowed from *"never
generate Clarion code examples"* to *"never hand-write per-control examples"*.

The reason it needed narrowing is worth stating, because the original rule was well intentioned. The
Clarion templates cover the **inbound** half only — `UltimateCOM.tpl` and the `UltimateCOM` class
handle instantiation, placement and events, with `Parm1..Parm6` arriving as StringTheory objects.
The class has no outbound member and the template generates no call sites, so **every** method call
and data payload is hand-written by the developer, with no guidance anywhere in the product. A
fixed, reviewed calling-convention block now fills exactly that gap, checked against the SoftVelocity
Help topics *"Parameter Passing to OLE/OCX Methods"* and *"Calling OLE Object Methods"*.

The original concern — that improvised per-control Clarion would likely be wrong — is preserved and
still enforced.

## Clarion Assistant's tools now run without the Clarion IDE

There is a new **`clarion-mcp-server`**: the editor-agnostic half of Clarion Assistant, as a standalone program that speaks **MCP over stdio**. Point any MCP client at it — Claude Code in **Sublime Text**, in **VS Code**, or in a plain terminal — and you get Clarion intelligence in an editor that is not the IDE. This is for Clarion developers who hand-code and would rather not work in the Clarion IDE at all.

```
clarion-mcp-server --stdio --solution C:\Path\To\Your.sln
```

It serves **61 of the 118 tools**: the documentation search across SoftVelocity and every third-party vendor you have installed, the knowledge base, the LSP tools, the dictionary and SQL schema tools, CodeGraph indexing and queries, file and Everything search, and Clarion class analysis. Indexing works fully — it reads your `.red` redirection file the way the compiler does, so a solution with one hand-written source file still indexes the ABC library behind it.

The other **57 are withheld on purpose**, because they drive the IDE itself: opening files in the editor, the app tree, the embeditor, the designer. An MCP client reads the tool list as a promise about what it can do, so a tool that could only ever fail is worse than one that is honestly absent. The addin is unchanged and still offers all 118.

**Both can be running at once.** If your IDE and a standalone server both index the same solution, they no longer collide: a full re-index wipes the database before rebuilding it, so two overlapping runs used to be able to destroy each other's work and leave a graph pointing at code that had been deleted from it. Whichever starts second is now turned away, and told which process holds the database. A run whose process is killed — a deploy, a crash, Task Manager — releases immediately and leaves nothing stale behind.


## The assistant now knows which dictionary your app uses ([#210](https://github.com/ClarionLive/ClarionAssistant/issues/210))

Ask *"compare the table definition for ITEM and ITEMSERVICE"* and the assistant used to go looking — through old SQL scripts, then through whatever `.dctx` it could find on disk, which for the reporter was a stale one from a different project. It had no better option: **nothing told it which dictionary the open app is bound to**, and the schema tools picked their database by scanning the solution folder and taking the first `.schemagraph.db` the filesystem listed. Unordered, silent, and wrong often enough.

Two things change. **`get_app_info` now returns the dictionary path** straight from the app's Global Properties, and a new **`get_app_dictionary`** reads that dictionary *live* from the IDE — tables, prefixes, drivers, and per table its fields, keys and relationships — with no export and no ingest, so it can never be stale. The comparison above is now one call. The SchemaGraph tools look at the open app's own dictionary database first, and **every schema answer now says which database it came from and why it was chosen**, so a wrong pick is visible instead of confidently wrong.


## The bundled language server now actually starts

If you run Clarion Assistant **without** Mark Sarson's ClarionLsp addin, the bundled language server has never worked — every `lsp_` tool failed with the server unreachable. The cause was three bytes: .NET builds the pipe to a child process from the console's encoding and flushes that encoding's byte-order mark as it does so, and those three bytes arrived ahead of our first message. The server rejected the message and blamed its header, which was perfectly correct, so the real culprit sat one step upstream of everything the error pointed at. It has been masked all this time because ClarionLive users generally *do* have ClarionLsp installed, and Clarion Assistant hands LSP work to it when it is there.

Go-to-definition, find-references, hover, document symbols and diagnostics now work with nothing installed but Clarion itself.


## The Clarion skills are a fifth of the size, and lose nothing

The nine largest skills have been rewritten: **313,000 characters down to 61,000**, roughly **78,000 tokens down to about 15,000** across the set. A session only ever loads each skill's short name and description up front; a skill's full body is read when the skill is actually used. So the saving shows up when a skill fires — a COM-control or embeditor task no longer pulls tens of thousands of tokens of instructions into the conversation before any work starts. ([#212](https://github.com/ClarionLive/ClarionAssistant/issues/212) — an earlier version of this note said skills load in full into every session, which was wrong.)

Nothing was deleted. The detail moved into 52 `references/` files that a skill reads *only when it actually needs them*, so invoking one now costs around 1,500–2,000 tokens plus whatever it genuinely reads, instead of the whole skill at once.

While rewriting them we also corrected the target framework. A find-and-replace had at some point turned every "net472 or net48" into "net48 or net48", which quietly made `net48` look like the only supported answer across seven files; the real COM controls target **net472**, and the skills now say so.

## New Chat no longer overwrites your CLAUDE.md ([#227](https://github.com/ClarionLive/ClarionAssistant/issues/227))

Opening a **New Chat** with no working directory set started the terminal in your user profile, and Clarion Assistant then copied its own instructions over `<working folder>\.claude\CLAUDE.md` on every launch — which there meant your **global** `%USERPROFILE%\.claude\CLAUDE.md`. The same code overwrote a hand-written project `CLAUDE.md`, and replaced `settings.local.json` wholesale, which is where Claude Code keeps your "don't ask again" permissions.

Clarion Assistant now **never writes into your user Claude folder** (`%USERPROFILE%\.claude`, or `CLAUDE_CONFIG_DIR` if set) — not `CLAUDE.md`, not `settings.local.json`. In a project it only refreshes a `CLAUDE.md` that begins with its own opening lines, and only creates `settings.local.json` or replaces the one-line file it wrote itself. Where it can't write the file, it hands its instructions to Claude on the command line instead, so every terminal still gets them. **If you were hit by this, your original global `CLAUDE.md` is not restored automatically** — restore it from File History, OneDrive or another backup; the [#227 thread](https://github.com/ClarionLive/ClarionAssistant/issues/227) lists the places to look.

Related, and older: the Clarion Assistant **status line has never worked**. Its `settings.local.json` was written with a UTF-8 byte-order mark, and Claude Code parses that file with `JSON.parse`, which rejects a BOM — so the whole file was ignored. Every file we write for a non-.NET reader is now BOM-free, and a build guard fails the deploy if one ever regresses.


## Clarion source stays in its own encoding ([#203](https://github.com/ClarionLive/ClarionAssistant/issues/203))

The `write_file` tool wrote every `.clw` / `.inc` back as **UTF-8**, whatever it was before. An `ø` stored in an ANSI file as one byte came back as two, and Clarion shows that as `Ã¸` — in the editor, and in every string literal the compiler bakes into your program. `append_to_file` appended UTF-8 onto ANSI files, leaving one file in two encodings, and creating a class from a model, generating a `.clw` from an `.inc`, appending method stubs and the structure designer all did the same.

All of them now write Clarion source in **the file's own encoding**: an ANSI file stays ANSI, a genuinely UTF-8 file (one with a BOM, or already holding UTF-8 characters) stays UTF-8, and new or all-ASCII source files use Windows' ANSI code page, the one the Clarion IDE uses. A character the file's code page cannot hold — an emoji, say — is **refused with an error** naming it, and the file is left untouched, rather than silently becoming `?`. Files already converted won't convert themselves back; restore them from version control or re-save them as ANSI.


## The bundled language server is now v1.0.5 ([#224](https://github.com/ClarionLive/ClarionAssistant/issues/224))

The server that ships with Clarion Assistant moves from v1.0.2 to **v1.0.5**, synced through a hardened `Sync-LspServer.ps1 -Pure` that now verifies the shipped server matches the pin ([PR #186](https://github.com/ClarionLive/ClarionAssistant/pull/186)). Along the way we found the installer had kept packaging **v1.0.0** since the v1.0.2 re-pin in September; no release carried that (5.8.x shipped 1.0.0 with a matching manifest), but 5.9.0 would have. The installer now takes its server from the same pin as everything else.


## Folding understands a LOOP closed by UNTIL or WHILE ([#222](https://github.com/ClarionLive/ClarionAssistant/issues/222))

A `LOOP` terminated by `UNTIL` or `WHILE` — valid Clarion, and the Language Reference's own example — never closed its fold, so it swallowed everything after it. The CA Editor and Embeditor now ask the language server for fold ranges ([PR #223](https://github.com/ClarionLive/ClarionAssistant/pull/223)), and the editor's own fallback, used while the server is starting or slow, closes a LOOP on `UNTIL` / `WHILE` too. A name like `While:Count` is not mistaken for a terminator.


## A LOOP closed by UNTIL or WHILE is no longer an error, and Ctrl+I keeps it level

Folding was not the only part of the editor that thought a `LOOP` needed an `END`. In an embed slot, the structure check underlined `LOOP ... UNTIL x` with *"LOOP is not terminated with END or '.'"*, and **Ctrl+I** indented the `UNTIL` line as part of the loop body — and everything after it one level too deep. Both now treat `UNTIL` / `WHILE` as closing the innermost `LOOP`, and only a `LOOP`: with an `IF` on top it is still an ordinary line, and the pre-condition form `LOOP WHILE x ... END` still needs its `END`.


## Ctrl+I no longer moves a loop's label off column 1

A labelled structure such as `MyLoop LOOP` — the label that `BREAK MyLoop` and `CYCLE MyLoop` name — had its label indented into the code column by **Ctrl+I**, and a Clarion label that isn't in column 1 no longer compiles. The formatter also never opened the structure, so its body stayed flush and its `END` closed the wrong block. A labelled `LOOP`, `IF`, `CASE`, `ACCEPT`, `EXECUTE` or `BEGIN` now keeps its label in column 1 and lays out exactly as the unlabelled form would.


## The language-server tools work from a plain Chat, and say why when they can't

Started with the **Chat** button rather than **Work With Open Solution**, the assistant's `lsp_*` tools had no solution even with one open in the IDE, so every call answered *"LSP not running"* — and `lsp_start` ignored the folder it was given, then blamed a *"client handshake"* that had never been attempted. The tools now follow the solution open in the IDE (and restart on it when you switch), `lsp_start` uses the folder or `.sln` you name, and a start that doesn't happen says which reason applies. **Find All References** also opens the file in the server before asking; without that, a request from the MAP line came back as a single zero-width hit, where the server finds the prototype, the implementation and a `START()` call. **Shift+F12** in the CA Editor no longer silently does Go to Definition.


## PostgreSQL: ingest no longer aborts on aggregates, and errors say what happened ([#201](https://github.com/ClarionLive/ClarionAssistant/issues/201), [#188](https://github.com/ClarionLive/ClarionAssistant/issues/188))

Indexing a PostgreSQL database that had a user-defined **aggregate** failed outright with `42809 wrong_object_type`, and the Index status cell said only *"error"*. Aggregates are now skipped (window functions are still indexed — only aggregates break `pg_get_functiondef()`), and the status cell shows the real message. **Test Connection** now says plainly when `Npgsql.dll` is missing, instead of showing the .NET loader error — and says something different when it is present but can't be loaded, so a broken install no longer looks like a missing one. Bundling Npgsql with the installer is still to come.


## A locked .app is reported as a lock ([#204](https://github.com/ClarionLive/ClarionAssistant/issues/204))

`build_app` and `generate_source` default to the app open in your IDE — which is the IDE holding it open — so ClarionCL failed with *"Could not gain access to MyApp.ap~"* / *"Cannot open application … (status 32)"*, reading exactly like a template or source error. The result now carries a **DIAGNOSIS** line saying the `.app` is locked by a Clarion IDE, most likely this one, and to close it there and retry.


## CA Editor and Embeditor: Mark Word on Ctrl+W ([#229](https://github.com/ClarionLive/ClarionAssistant/issues/229))

**Ctrl+W** now marks the word at the caret. A word here is letters, digits and underscores — the
colon is deliberately not part of one — so with the caret anywhere in `LOC:CustomerName` it marks
just `LOC` or just `CustomerName`. Double-click already takes the whole prefixed name, so this is
the one way to take either half on its own.

Press **Ctrl+W** again while that half is still what is selected and it widens to the whole
`LOC:CustomerName` — exactly the word double-click would take. A third press leaves it there. It
works at every cursor, only ever changes the selection (so it works outside the editable embed slots
too), and can be rebound in the gear panel's **Keyboard** section like the other editor commands.
Requested and contributed by Rick Martin ([PR #231](https://github.com/ClarionLive/ClarionAssistant/pull/231)).

## The embeditor tools reach large procedures, and never save over your unsaved edits ([PR #198](https://github.com/ClarionLive/ClarionAssistant/pull/198))

On a large procedure, `apply_embed_edits` and `open_procedure_embed` always came back *"UI thread did
not respond within 30s"* — while the IDE was neither busy nor blocked. Every tool that runs on the
IDE's UI thread shared one fixed 30-second budget, and a single native embeditor open can take up to
45 seconds on its own. The work could never finish in the time it was given.

The four slow tools — `open_procedure_embed`, `apply_embed_edits`, `save_and_close_embeditor` and
`warmup_abc` — now get **180 seconds**. Everything else keeps 30, so the timeout still catches a
genuinely wedged IDE. If you need more, add `Mcp.UiToolTimeoutSeconds` to
`%APPDATA%\ClarionAssistant\settings.txt`: it raises the budget for every UI-thread tool, never
lowers a tool below its own minimum, and is held between 5 and 600 seconds.

`apply_embed_edits` can now also work on a procedure you **already have open** in the embeditor,
instead of refusing — but only when that embeditor has **no unsaved changes** and no CA Embeditor is
showing it. Its save persists the whole buffer, so writing into a buffer holding your own unsaved
edits would have saved them for you. Otherwise it refuses, writes nothing, and says why.

**A call that timed out no longer saves late.** Before, the tool carried on after the caller had been
told it failed, and could still write and save. Now a call the IDE never started does not run,
`apply_embed_edits` discards its writes instead of saving, and `save_and_close_embeditor` does not
save. A failed save rolls our writes back, and the messages say what actually happened — including
when a rollback could not be confirmed, rather than claiming one.

## `lsp_diagnostics` no longer calls a file clean too early ([#216](https://github.com/ClarionLive/ClarionAssistant/issues/216))

`lsp_diagnostics` is how the assistant checks its own edits, and it could answer *"no errors"* before
the language server had finished looking. It decided the analysis was done from a signal that turned
out not to be the end of it, or from a short quiet period.

Since v1.0.4 the language server ends every analysis with an explicit status message for that file,
and the bundled client now waits for it: only a **complete** for this file, at the version we sent,
ends the wait. If the time runs out first, the answer is still *"pending"*, never *"clean"*. A server
too old to send the status keeps the previous behaviour. With Mark Sarson's ClarionLsp addin
installed, requests go through the addin, and this wait is its job — clarion-lsp v1.4.3 does it.

## CA Editor: squiggles on the right line, the whole font list, and no white flash ([#176](https://github.com/ClarionLive/ClarionAssistant/issues/176), [#184](https://github.com/ClarionLive/ClarionAssistant/issues/184), [#195](https://github.com/ClarionLive/ClarionAssistant/issues/195))

**Squiggles no longer land lines off.** The editor painted whichever diagnostics reply came back
last. A slow reply to an older request could overwrite a newer one and draw its line numbers over a
buffer that had since changed. Each reply is now checked against the request and the buffer version
it was for; a stale one is dropped and a fresh check runs instead.

**The font box shows the whole list.** With a font set, opening the Font family list showed only
that font, because the box was a type-in field and the browser filters its list by what is already
typed. Nobody needs to type a font name, so it is now a **plain dropdown**: *Default* plus the same
fonts, the whole list every time, and a pick applies at once. A saved font that is not in the list —
an older fallback list such as `Consolas, 'Courier New'`, or a font imported from VS Code — is kept
as an extra entry and shown selected, rather than dropped.

**No white flash when the editor opens.** The CA Editor and the CA Embeditor could show a white or
light panel for a moment before the editor painted, which on a dark theme looks like a flash. Every
surface shown before the editor is ready now uses the editor's own background, and under **Windows
High Contrast** it uses the contrast theme's window colour, so a dark contrast theme no longer gets a
near-white flash first.

## Completion lists a member once ([#187](https://github.com/ClarionLive/ClarionAssistant/issues/187))

Member completion in the CA Editor showed some methods twice — the report's screenshot had four
StringTheory methods doubled. The language server itself had sent them twice, and nothing removed
the repeat before the list reached the editor. Identical items are now listed once. Overloads that
the server labels with the same bare name but a different signature are still listed separately.

Found along the way: in the CA Embeditor, when the buffer already started with `MEMBER` or `PROGRAM`,
every position sent to the language server landed **one line low**, and every answer — completion,
go to definition, hover, outline, folding, diagnostics — came back one line high. That is fixed. It
is not shown to be what the reporter hit, and a separate report in the same issue, about completion
after `st.` in a data embed, could not be reproduced and is not claimed fixed here.

## The embeditor finds generated modules through your redirection file ([PR #228](https://github.com/ClarionLive/ClarionAssistant/pull/228))

The CA Embeditor looks up the procedure's generated `.clw` so that diagnostics and navigation run
against the real file. It only ever looked **next to the `.app`**. If your `.red` sends generated
source somewhere else, it was never found, and every embed quietly fell back to a made-up path that
does not exist on disk.

The lookup now goes through the redirection file too. It searches the build sections (`[Debug32]`,
`[Release32]`, `[Debug]`, `[Release]`) before `[Common]`, and honours the `.app` folder's own `.red`
ahead of the solution's, as Clarion does.

**One behaviour change to know about.** Clarion only honours a local `.red` named for the running
version — `Clarion120.red`, say — and ignores any other `*.red` in the folder. Clarion Assistant
used to take the first `*.red` it found in a solution or app folder. It now follows the same rule as
Clarion, so a misnamed or backup `.red` is ignored here too. If a lookup changes after upgrading,
check that the local `.red` has the version's name.

This came out of the investigation of [#179](https://github.com/ClarionLive/ClarionAssistant/issues/179), but it does
**not** fix #179's access violation.

## A hung Clarion no longer sits on the multi-instance roster forever ([PR #208](https://github.com/ClarionLive/ClarionAssistant/pull/208))

When one Clarion IDE hangs without exiting, it kept its place in the list of running instances that
the others check for procedure conflicts. A process that still exists looked alive, even if it would
never respond again, so every other instance kept colliding with it until a reboot.

An instance that stops responding is now dropped from the roster after about **two minutes of not
responding continuously**. A single slow answer is not enough, because a busy IDE — mid-build,
mid-generation, loading a large dictionary — gives the same answer, and dropping it would hide its
conflicts for the length of the build. An IDE that was dropped while busy puts itself back on the
roster once it responds again.

## CA Explorer matches the running Clarion to the right version ([#209](https://github.com/ClarionLive/ClarionAssistant/issues/209))

When Clarion's own record of the current version is missing, stale, or says *"(Current ...)"*, Clarion
Assistant works out the version from the running `Clarion.exe`'s bin folder. It took the **first**
version entry with that folder, but several entries share one: every install registers its
Clarion.NET compiler on the Win32 IDE's bin. In the report, `Clarion.NET 4.0.13372` came before
`Clarion 11.0.13372`, so the IDE was treated as its own .NET compiler.

It now prefers the Win32 entry and the one whose build number matches the running exe. That
matters beyond the CA Explorer banner and recent-files list: the same version decides the `.red`
file, the language server and CodeGraph.

## `append_to_file` no longer adds a blank line ([#232](https://github.com/ClarionLive/ClarionAssistant/issues/232))

`append_to_file` always wrote a line break before the new text. Most files already end with one, so
nearly every append left a blank line. It now adds the break only when the file has content that
does not already end in one. The encoding handling from [#203](https://github.com/ClarionLive/ClarionAssistant/issues/203)
is unchanged.

## Large procedures no longer crash the IDE from the CA Editor or Embeditor

On a very large generated module — 86,722 lines, 3.2 MB — the 32-bit Clarion IDE could die with an
out-of-memory crash while a CA Embeditor was open on it. The editor sent its **whole buffer** to the
IDE with every hover, completion, signature help, go to definition, diagnostics, outline and
folding request: several megabytes of copies each time, many times a second while you type.

Both Monaco editors now send the buffer **once per edit**, and each request only names the version it
is about. Measured on a 3.2 MB buffer: twenty hovers without an edit went from 66 MB of traffic to
3.3 MB. The diagnostics timeout also grows with the size of the buffer (up to 60 seconds), so a big
module is not given up on after the same few seconds as a small one, and a newly opened procedure's
diagnostics no longer queue behind the previous one's.

That fixed the crash but not the wait: completion, hover and squiggles were still slow on a module
this size. The next entry is how that got fixed.

## Completion, hover and squiggles are instant on large procedures

On that same 86,722-line module, typing in the CA Embeditor meant waiting on the language server.
Completion showed *"Loading…"* for four seconds and then *"No suggestions"*. A hover took anywhere from
1 to 35 seconds. A `DO` of a routine that doesn't exist took about **five minutes** to get its squiggle.
The native Clarion embeditor answers all of these instantly, and that is the bar.

We measured before changing anything. The language server re-analyses the **entire** module on every
edit, whatever you send it, so no amount of tuning on our side would make it fast on a file this size.
The same server is just as slow in VS Code. So Clarion Assistant now answers first, from what it
already knows, and treats the language server as a late extra:

- **Completion** comes from the procedure you are in: its locals, **parameters**, routines, group and
  queue fields, and the members of any class in scope. That includes `SELF.` inside a
  `ThisWindow.Init` method, with inherited members such as `WindowManager`'s. It also covers
  solution-wide procedures and globals from CodeGraph, `PRE:` fields from the **live** dictionary
  (no `ingest_schema` needed), and Clarion's keywords and built-ins.
- **Hover** works the same way, and keywords, attributes and built-ins now show **what they do**.
  Hover `DERIVED` and you get *"CLASS method attribute. Specifies the PROCEDURE is a derived method of a
  CLASS structure…"*, with a signature where there is one (`CLIP(STRING string)`, returns `STRING`).
  The text comes from the language server's own data files, which were already installed.
- **Squiggles** from Clarion Assistant's own checks, such as unbalanced structures and a `DO` of a
  missing routine, are painted as soon as they are computed. The language server's squiggles are
  added when they arrive and never hold ours back.

Measured in the IDE on that module, from keystroke to list on screen: completion **43 ms**
typical, **119 ms** at worst over a session. A hover appears in **7–35 ms**. The `DO` squiggle appears
in well under a second.

Two things make that possible in a 32-bit IDE:

- **Typing no longer ships the module around.** Each keystroke used to send the whole 3.2 MB buffer
  to the IDE. It now sends the few hundred characters around the caret, and the procedure's data
  section travels as a short fingerprint unless you have edited it. The full buffer goes over only
  when you pause for 400 ms.
- **CodeGraph lookups stay fast.** They used to open the database afresh and scan it on every
  keystroke, at 150–500 ms each on a 422,000-symbol solution. They now keep one connection open and
  use new case-insensitive indexes: about **0.2 ms** a lookup. Existing CodeGraph databases get the
  indexes automatically, built once in the background the first time they are used (about a second
  on that solution), so there is nothing to re-index by hand.

Along the way:

- **Locals declared before a `ThisWindow CLASS`** were invisible to completion and hover in every ABC
  procedure, and `Init` and `Kill` were offered as if they were local procedures. The scope scanner
  was reading the class's method prototypes as the procedure's own header.
- **Completion no longer offers other procedures' parameters as if they were globals.**
- **Squiggles now match the text on screen after a save and reopen.** When the language server was
  still busy, Clarion Assistant would paint diagnostics it had cached for an **older** version of the
  file, sometimes the file on disk. That put squiggles on the wrong lines, even inside comments,
  while missing the real errors. It now waits for diagnostics that belong to the text you are
  looking at.
- **Diagnostics logging** says why the language server pass was skipped. A language-server crash is
  now logged with its exit code and last error output, instead of leaving no trace.
- **The bundled language server starts as soon as a solution opens.** It used to wait for a Clarion
  Assistant chat tab, so with only the IDE and a CA Embeditor open it never started at all.

On a module this size the language server itself still rarely answers within its time limit. What it
adds on smaller files still arrives, merged in the moment it does.

## The header has tabs: Solution, Schema Sources and Source Control

Schema Sources and Source Control are settings of the **solution**, not of a chat. Until now they
lived in a collapsed *"Solution Settings"* bar inside each chat tab, and most people never found
them. They are now tabs of the header itself:

- **Solution** is the header you know: the solution, the Clarion version, the RED file and CodeGraph
  with Reindex and Update.
- **Schema Sources** lists the databases linked to the solution, and the tab shows how many there are.
  Manage Sources and Index All work as before.
- **Source Control** links the solution to a GitHub or Bitbucket account and repo.

Both follow the solution selected in the header, and look the same from every tab, Home included.

Also in the header:

- **It has a fixed height.** The drag bar under it is gone.
- **⧉ beside SOLUTION** copies the solution's full path to the clipboard.
- **RED is a link.** Click it to open the `.red` file in an IDE editor tab. When no redirection file
  could be found it stays a warning and is not clickable.
- **The ◎ "Show/hide LSP Diagnostics bar" toggle is gone**, and so is the bar. The squiggles in the
  CA Editor and CA Embeditor show the same diagnostics where you are looking.

## Clarion Assistant follows Build > Set Clarion Version

The IDE keeps a Clarion version per solution, set with **Build > Set Clarion Version**. Clarion
Assistant read it only at startup or when the solution changed, and a version picked in its own
**VERSION** box was one global setting that beat the IDE forever — and only some of Clarion
Assistant honoured it, so the CodeGraph library index, the Data pad and the CA Explorer header could
each be using a different version from the language server.

Now **Clarion Assistant shows the Clarion version the IDE has selected and no longer has its own
version picker.** VERSION is a read-only display. Clarion Assistant follows the IDE's choice when you
change it, reloading the `.red` and restarting the bundled language server if the version moved, and
**every part of Clarion Assistant uses the same version.** With the IDE on **(Current Version)**, or on
the running Clarion's own version (Clarion stores that choice as "Current" too), VERSION shows the
running Clarion's version, marked **(IDE)**. The ↻ button re-reads the IDE's choice.

Two places to set one version was what made it confusing. A Clarion 12 IDE on (Current Version) could
show `Clarion 10 Active And Updated (saved)`, because a version saved in the old dropdown, by any
Clarion IDE on the machine, could outrank the IDE. Versions saved that way are now simply ignored.

## CA Explorer's header says what it means

The CA Explorer header read like `Clarion10v8 · clbrws` — a version folder name and the solution name
run together, which did not match the Assistant's VERSION box either. It now shows one fact per
labelled line: **APP** (the open `.app`, or **SOLUTION** when no app is open), **VERSION**, **ROOT**
(that version's folder) and **RED** (the active redirection file). Clicking **APP** shows the file in
Windows Explorer and clicking **ROOT** opens the folder. A path that is no longer there says so
instead of doing nothing.

## CA Embeditor: the caret and Enter stay with the code

Two fixes from install testing, for problems older than 5.9.0:

- **No more lines padded out to column 125.** With **Can move caret behind EOL** on and word wrap
  on, clicking in the empty space beside a wrapped line was read as a click far past the end of the
  line. The caret's goal column was set to roughly the window width and stayed there: every later
  up/down padded the line it landed on out to that column, and Enter on such a line carried the
  spaces onto the next. Only reopening the procedure cleared it. A click there now behaves as a
  normal click.
- **Enter after END, Enter and Ctrl+I re-indent from the code you can see.** The formatter works
  out indentation by counting structures from the top of the buffer, which in the embeditor is the
  whole generated module. Generated code it does not model, such as `OMIT` / `COMPILE` blocks, left
  that count off by the time it reached your embed, so an `IF ... END` block could be thrown out to
  column 125. Re-indenting now keeps the block anchored to the code around it, labels stay in column
  1, and a re-indent that would move a line more than 40 columns is refused.

- **Member completion on `GROUP` / `QUEUE`** is right again ([PR #219](https://github.com/ClarionLive/ClarionAssistant/pull/219)): a one-line `GROUP(T) END` no longer swallows the procedure's locals as its fields, and a typed `QUEUE(Type)` no longer uses its incomplete inline field list as the member filter.

- **A trailing period on an ordinary statement** now closes its structure in the embed-slot structure check, ending false *"unterminated"* warnings ([PR #226](https://github.com/ClarionLive/ClarionAssistant/pull/226)).
- **Ctrl+D** no longer opens the wrong designer when a structure keyword is used as a plain label, such as a variable named `report` ([PR #220](https://github.com/ClarionLive/ClarionAssistant/pull/220)).
- **The CodeGraph indexer's window buttons** work again — the editor's focus guard was taking focus back from them ([PR #217](https://github.com/ClarionLive/ClarionAssistant/pull/217)).
- **Knowledge entries can be retired**: `supersede_knowledge` and `remove_knowledge` let a wrong entry stop being injected, instead of only being contradicted by a newer one ([PR #199](https://github.com/ClarionLive/ClarionAssistant/pull/199)).


## CA Debugger: the execution line and Run to Cursor work in the CA Editor

With the CA Editor (Monaco) in front, the CA Debugger painted **no execution-line marker**, because the navigation it used only scrolls. The CA Editor now paints the debugger's current line itself and keeps it across reloads and reopen. Right-clicking now offers **Run to Cursor**, which runs a paused debug session to the caret without going to the pad toolbar, and refuses rather than guessing if its tab did not become the active window. Clarion Assistant finds the debugger at runtime by assembly identity, so nothing changes if it isn't installed.


## Under the hood

- **Messaging in IDE terminals.** Claude Code 2.1.265 stopped resolving the MultiTerminal channel supplied on the command line, so every IDE terminal printed *"no MCP server configured with that name"* and quietly fell back to polling. The channel now arrives through the plugin.
- **Deploy is stricter.** It refuses to deploy onto a running Clarion, never reports success on a partial copy, fails when the shipped language server does not match its pin, and is gated on the BOM guard — which now also fails if it scanned nothing, rather than passing vacuously. `deploy.ps1` parses under Windows PowerShell 5.1 again.
- **The shipped language server is checked, not just its source.** Deploy and the installer build now hash the `server.js` they are about to ship and compare it with the hash recorded for the pinned version; before, only the source checkout's commit was compared, which a stale or overlay build could pass. A proven mismatch is refused, and shipping one anyway takes the new `-AllowUnpinnedLsp` switch. `Sync-LspServer.ps1 -Pure` checks the repository and tag before building, and refuses a source tree that is not a git checkout unless `-TrustNonGitTree` is passed ([PR #191](https://github.com/ClarionLive/ClarionAssistant/pull/191)).
- **`deploy.ps1 -Version all` starts faster.** Looking for Clarion installs, it scanned every mounted drive, network shares included, for every version before printing anything. It now scans local fixed drives only ([PR #211](https://github.com/ClarionLive/ClarionAssistant/pull/211)).
