What's actually wrong

Six stacked zones compete for attention before you reach a single file. Worse — three of them are the same control and two of them are search boxes that search different universes.

1
Three controls, one job Every Quick Location chip posts pickFolderAndLoad — it opens the same multi-select file picker as “Load File…”, just rooted elsewhere. They are not folder browsers. “Last folder” is simply the folder that picker starts in. So Load File + Last folder row + 5 chips = one button with a dropdown.
2
Two identical-looking search boxes The top one searches the whole redirection index (20k files). The bottom one filters the recents list below it. Same shape, same placeholder grammar, totally different scope, 200px apart. This is the single biggest “what am I looking at” cost.
3
The filter radios are always-on chrome Six radios + a mask box occupy ~55px permanently, but they only matter while you are typing a query. Pure standing cost.
4
“Last folder” is a setting dressed as content It gets a full-width labelled row and a duplicate chip in Quick Locations. It is a preference — it belongs in a menu, not in the reading flow.
5
Section headers outnumber content “Quick locations” + group headers + the italic class note + the truncation hint = four grey texts before three actual files.

What must survive

  • Redirection type-ahead — the star feature; in-memory index, no disk I/O per keystroke.
  • Trace — niche but irreplaceable when a .red lookup goes wrong.
  • Class pair folding — one row opens .inc + .clw as two editors.
  • Native drop strip — must stay docked at the bottom (WebView2 strips real paths).
  • Per-solution recents bucket — hence the 📦 version banner.

Pick a variant tab above → each one attacks these five in a different order.

my recommendation

A — One box, one list

The core move: the recents list is just the empty-query state of the search. One field, one result surface, one mental model — “everything I can open, filtered.”

What changed

  • Two search boxes → one. Empty → recents, grouped as today. Typing → Recent matches first (you almost always want the file you touched yesterday), then Redirection matches below. Nothing is hidden, nothing needs choosing up front.
  • Radios → a type dropdown inside the field. Six always-on radios become one 90px control that reads as part of the query. Custom mask opens a small popover.
  • Load File + Last folder + 5 chips → one split button. Open… browses from the last folder; the caret lists LibSrc / Accessory / Solution / Last folder / your pins / Pin a folder / Set default folder. Same actions, ~110px of chrome reclaimed, and “last folder” finally reads as the setting it is.
  • Group headers → count pills. Answers your tabs question without a second tab row (see B). All is the default merged view; click a pill to focus one kind. Counts are visible at rest, which the current headers only give you after scrolling.
  • The italic class note moves onto the Classes header as a quiet opens .inc + .clw hint — same information, one line instead of two.
  • Redirection rows show their .red section ([Copy], [Source]) — free from the index we already have, and it's the thing you actually want to know when two files share a name.
  • Trace stops being a permanent button and becomes an action on the Redirection group header, where it makes sense (“trace this name”).

Recent compares ★ new

Today Compare… is the one action that records nothing — you re-pick both files through two dialogs every single time. A compare isn't a file, it's a pair, so it gets its own group and rides all the same machinery:

  • ⇆ Compares group + count pill, sitting above Classes because a compare is recent activity, not a library. Row click re-runs it — zero dialogs.
  • Pin a pair (★) and it sticks to the top of the group forever. That's your “same pairing several times” case: pin it once, it's one click for the rest of the project.
  • Split button on Compare… ▾ lists the last few pairs, so you can repeat without scrolling the list at all. Click the caret in the mockup.
  • Rows collapse what's redundant — the labelling adapts to why you're comparing:
    • same name, two folders → clbrws005.clw ⇆ 2 locations with both dirs below (version-vs-version)
    • same folder, two names → StringTheory.inc ⇆ .clw with the dir once (pair diff)
    • both differ → full name ⇆ name and both dirs (backup diff)
  • ⇄ swaps sides — left/right matters in a diff and re-picking to flip it is pure friction.
  • The omnibox searches pairs too — matching either side surfaces the compare. Try the typing sim.
  • Class rows record pairs too — decided. The ⇆ inc↔clw action writes a compare like any other: the two halves are genuinely tied together (method definitions must track their implementations), so a recorded inc↔clw pair is a real working artifact, not noise. Cap stays ~20 with pinned pairs immune, so deliberate compares can't be pushed out.

Implementation: add recentCompares:[{a,b,ts,pinned}] to explorer-recents.json (capped ~20, move-to-front dedup on the normalized unordered pair so A/B and B/A are one entry), and have MonacoFileOpener.Compare record it — it currently doesn't. Same per-solution bucket as recents, so compares follow the 📦 version banner.

Cost / risk

  • Merging the two searches means one keystroke path filters two data sources. Cheap — both are already in-memory arrays.
  • Enter is now ambiguous (recent vs redirection hit). Fix: Enter opens the highlighted row, highlight starts on the first Recent match.
  • Losing the always-visible ext radios costs a click for users who switch filters constantly. Worth watching.

Try “simulate typing” on the mockup to see the query state.

B — Groups become tabs

Underline tabs replace the group headers. The first tab, Recent, is the merged chronological list — that's the important part; without it, tabs would destroy the “what did I touch today” view entirely.

Why it works

  • Flattest possible list — no headers, no italic notes, no collapse chevrons. Pure content.
  • Counts sit in the tab, so the shape of your recents is visible at rest.
  • Each tab can have its own sort and columns — Classes could sort by class name, Templates by vendor folder. Headers can't do that.
  • Reclaims the most vertical space of the three variants.

Why I'd hesitate

  • Tabs inside tabs. There's already a Data / Files / Cheat Sheet row 30px above. Two tab rows in a 620px pad is a real orientation cost — you have to remember which row you're in.
  • Hidden state. If the tab remembers where you left it, you open the pad on “Templates” and your recent .clw is invisible. If it doesn't remember, tab choice is never durable and the tabs are just slow pills.
  • Groups are derived and volatile. A tab can be empty (no templates yet in a fresh solution). An empty header hides itself gracefully; an empty tab is dead furniture you still have to render.
  • Pills in variant A give ~90% of this benefit without a second tab row — that's the trade to argue about.

If you like this direction, the hybrid worth building is: A's pills, styled as underline tabs — visually B, behaviourally A (All stays the default, empties auto-hide).

C — Flat & calm

Delete the grouping entirely. One list, strict recency, icon carries the type. Everything that isn't a file is either in the toolbar or revealed on demand.

What changed

  • No group headers, no counts, no notes. Nine files render in the space that currently holds three. The 📗/🧩/📘 icon and the .inc .clw badges already tell you the kind — the headers were restating the icons.
  • Type filters appear on focus and collapse when you leave the field. Zero standing cost, full power when you're actually filtering.
  • Toolbar is one row. Search + Open▾ + Compare + overflow (⋯ = Trace, Refresh, Set default folder, Pin folder, Clear recents).
  • Timestamps compress to 5h / 1d / 5d / Jul 2. The verbose “5 days ago” column was ~90px of repetitive text.
  • Strict recency answers the actual question — “what was I just in?” — which grouping currently buries under a Classes section that may be a week stale.

What you lose

  • “Show me all my templates” now needs the type filter instead of being permanently visible. That's the whole bet: is browsing-by-kind common enough to pay for headers on every render?
  • Pinned files lose their dedicated section — they'd need to sort to the top with a 📌 marker instead.
  • The class-pair explanation has nowhere to live; it becomes a tooltip on the badges.

C is the honest test of your instinct. If, after a week on C, you never miss the groups — they were chrome. If you do miss them, A's pills are the cheapest way to get them back.

the pills survive

A+ — Adding .md / .json / .html / .xml

There are two different filters in variant A and it's worth separating them, because only one of them scales with file types — and it's already a dropdown.

1. The type filter — in the search field

This one queries the 20,000-file redirection index, where literally any extension can turn up. It must enumerate types, so it was always going to be a dropdown — it's the All types ▾ control. Click it in the mockup: new formats just add a Docs & data section to a menu that was already grouped. It absorbs ten new extensions at zero visual cost.

2. The pills — below the toolbar

These are not a type catalogue. They're groups over your recents — files you have actually opened. That's the difference that saves them:

  • They don't enumerate what's possible, only what's present. Empty groups already auto-hide (the current code does this too). A pure-Clarion solution never renders a Docs pill at all — hit “solution: mixed” in the pad header to watch the row shrink.
  • One new group, not nine. The trap is a group per extension. Don't: fold every non-Clarion format into a single 📄 Docs & data bucket. Ten extensions, +1 pill. The extension is already on every row, colour-coded — the group doesn't need to repeat it.
  • Ceiling is ~7 and it's fixed: All, 📌, ⇆ Compares, Classes, Templates, Source, Docs. That's the whole taxonomy, and it does not grow when you add formats — only if we add a genuinely new kind of thing (as Compares was).

If they ever do overflow

Cheap insurance, worth building once: order pills by count and let the tail collapse into a dashed ⋯ N more chip that opens as a menu (shown in the mockup). One line, always — never wraps, never scrolls sideways in a 620px pad.

The filter is the easy half

What actually makes these formats work isn't the pills — it's four small things on the host side:

  • Language mapping in MonacoFileOpener — ext → Monaco language id. Monaco ships json / html / css / javascript / xml / markdown / sql grammars already, so this is a lookup table, not a parser. This is what “formatted properly” means for syntax colour.
  • Actual formatting — only JSON, HTML and CSS have built-in document formatters; .md and .xml don't, so Format Document silently no-ops on them. Worth knowing before it reads as a bug.
  • Drop-strip whitelist — IsAllowedDropExtension gates the native drop strip; new formats must be added or dropping them silently does nothing.
  • Extension colours in the row renderer, plus KindOf() in ExplorerFileClassifier returning the new docs kind — otherwise everything lands in Other.

Markdown routes elsewhere — verified 2026-07-28

.md is the one format that should not open in Monaco. ClarionMarkdownEditor (Mark Sarson's fork — split-pane live preview, WebView2 + a self-contained HTML page, architecturally the same shape as our Monaco surface) already exists and is installed at C:\Clarion12\accessory\addins\MarkdownEditor. Hence the MD editor badge on the row — same honesty as the Classes group telling you it opens two editors.

Three facts that decide the integration:

  • It exposes MarkdownEditorViewContent : AbstractViewContent with Load(string) / Save(string) — a proper document view content, the same contract family as our ModernEmbeditorViewContent. It is genuinely hostable as a file tab.
  • But its .addin declares NO <DisplayBinding> — only a Pad (Ctrl+Alt+M) and a View menu item. So the IDE never routes .md to it on its own. Today, opening a .md gets you the plain text editor.
  • The build installed here is v1.0.0 (Jan 2026) — John's stale original, not Mark's v1.1.x (tabbed multi-file, save-corruption fix, open-from-URL). PR #4 has been open since Feb; neither repo is archived; CA issue #27 untouched since May. The canonical-repo question is still unresolved.

Decided: .md routes to Mark's editor, and no “open as text” fallback is needed — confirmed in the shipped page: it has editorPane + preview-pane, a split toggle (SplitDirection) and scrollSyncEnabled/syncScroll with a checkbox. It is the raw editor with a live preview beside it, scrolling together. A Monaco fallback would be strictly worse.

The one tweak worth PR-ing: add <DisplayBinding> for .md to his .addin. Then CA just doesn't hijack the extension — route .md through the IDE's normal open path and binding resolution does the rest. CA ships zero markdown code. Bridge if that's slow: resolve MarkdownEditorViewContent reflectively, Monaco fallback when absent.

Bundling it with our installer

Licensing is fine — Mark's fork is MIT (John's upstream has no license at all, worth fixing as part of the canonical call). Redistribution just needs the LICENSE + copyright carried along. Two real risks though:

  • Version collision. If our installer writes accessory\addins\MarkdownEditor and Mark ships his own releases, last-installer-wins — including silent downgrades (user installs his v1.3.0, later reinstalls CA, gets our older bundle). Guard the [Files] block with a Check: that compares GetVersionNumbersString and only overwrites when ours is newer. Never blind-copy.
  • PR first, then bundle. If we bundle a locally-tweaked build (his v1.2.0 + our DisplayBinding) while the PR is unmerged, our artifact permanently diverges from his releases and the collision problem compounds. Land the DisplayBinding upstream, then redistribute his released artifact unmodified — we stay a pure redistributor with nothing to maintain.
  • Consider the marketplace channel instead of the installer (ClarionLive/clarionassistant-marketplace, configure.ps1 -InstallPlugin) — optional-by-design, and sidesteps last-writer-wins entirely.
  • Installer gotchas that bite here: ISPP #ifexist is file-only, so a directory guard silently drops the whole [Files] block — probe a sentinel file and warn on skip; and verify the deployed folder against the hand-list, which has drifted before in clean-install-only ways.

Currently installed here: v1.0.0 (Jan 2026) — three releases behind and missing the v1.0.2 save-corruption fix. Worth updating independently of any of this.

Hard constraint either way: CA must consume this at runtime only — never as an .addin <Dependency>. A coerced dependency is still a hard one in this IDE, so declaring it would stop ClarionAssistant loading on any machine without the markdown addin installed.
